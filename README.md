# 애니 — 사내 업무 AI 비서

임직원이 **질문 한 줄로** 담당 사건의 업무 상태를 확인하고, **기록 초안을 제안받는** 사내 AI 비서 **애니**입니다.
묻는 말에만 답하는 챗봇이 아니라, 창을 열면 오늘 챙겨야 할 일을 **먼저 알려 주고**,
필요한 기록·일정 등록을 **먼저 제안**합니다. 실제 반영은 사람이 확인해야만 됩니다.

> 법률 사무소에서 실제로 개발·운영 중인 사내 에이전트(임직원 500여 명 사용)의 설계를
> **합성 데이터로 다시 구현한 공개본**입니다. 회사 코드·데이터는 한 줄도 포함되어 있지 않으며,
> 등장하는 인물·사건·기관은 전부 시드 고정 난수로 만든 것입니다.

```
Python · FastAPI · httpx(OpenAI 호환 LLM 직접 호출) · SQLite · Vanilla JS · Web Speech API
```

## 무엇을 대신해 주는가

다루는 범위는 사건 **내용**이 아니라 **업무 상태**입니다. 일정, 담당 건수, 담당자, 처분권자 등록 여부,
종결 결과, 계약 금액처럼 **놓치면 안 되는 값**들입니다.

| 기존 방식 | 애니 |
|---|---|
| 사건관리 화면에서 사건 검색 → 개요·일정·담당자·처분권자 탭을 옮겨 다니며 눈으로 확인 | "박민수 사건 다음 기일 언제야?" 한 줄 |
| 기록을 남기려면 해당 탭을 찾아 폼 작성 | "면담 기록 남겨줘: …" → 제안 카드 → **반영** 클릭 |
| 놓친 일정·미등록 항목은 직접 찾아야 함 | 창을 열면 **3일 내 일정 · 처분권자 미등록 · 장기 미면담**을 먼저 보여 줌 |

사내에는 이미 사건 단위 에이전트가 있었습니다. URL 에 사건 ID 가 있어 범위가 자동으로 정해지는 구조였죠.
이 에이전트는 **사건을 고르지 않고 시작**합니다. 이름만 있는 질문을 받아 그 사람이 맡은 사건 안에서 대상을 찾아냅니다.
그래서 가장 공들인 부분이 **권한 경계**입니다.

## 구조

```
질문 (+ 화면 컨텍스트: 보고 있는 사건 ID, 음성 입력)
   │
   ▼  POST /api/ask ── 로그인 토큰에서 emp_id 추출 (요청 본문으로 받지 않음)
system prompt(고정) + 대화 이력(최근 8턴) + 질문
   │
   ▼  ┌─ 도구 호출 루프 (최대 6회, 직접 구현) ─────────────┐
      │  LLM 스트리밍 호출 (OpenAI 호환 /chat/completions)  │
      │    ├─ 본문 조각 → SSE 로 즉시 전송                  │
      │    └─ tool_calls 수집                              │
      │  도구 병렬 실행 (asyncio.gather + to_thread)        │
      │    └─ 모든 조회에 권한 경계 절 강제                  │
      │  결과를 컨텍스트 창에 맞게 줄여 재투입               │
      └────────────────────────────────────────────────┘
   ▼
후처리: 출처(바로가기) · 선택 버튼 · 쓰기 제안 카드  ← 전부 도구 원본에서 생성
   ▼
SSE (stage: plan → tool → answer → done)  →  대화 턴 보관
```

**RAG 가 아니라 Tool Calling 입니다.** 사건 정보가 관계형 DB 에 정규화되어 있어서, 유사도 검색보다
정확한 조회가 맞는 문제였습니다. 검색은 질문을 조각내 의뢰인명·사건명·사건번호·유형을 LIKE 로 찾습니다
([`search.py`](backend/app/agent/search.py)).

**도구 15개** — 읽기 10 / 쓰기 제안 5 ([`registry.py`](backend/app/agent/registry.py))

| 구분 | 도구 |
|---|---|
| 사건 찾기 | `find_cases` `find_authorities` |
| 사건 내용 | `get_case_overview` `get_case_authorities` `get_case_meetings` `get_case_schedules` `get_case_employees` `get_case_summary` |
| 전체 훑기 | `list_my_cases` `list_my_schedules` |
| 쓰기 제안 | `propose_meeting_note` `propose_meeting_update` `propose_meeting_append` `propose_authority_link` `propose_schedule` |

## 설계에서 신경 쓴 지점

### 1. 권한 경계를 한 곳에 — LLM 이 만든 값을 권한 판단에 쓰지 않는다

[`visibility.py`](backend/app/agent/visibility.py) 한 파일에 규칙을 모았습니다. 도구마다 따로 판단하면 한 군데만 빠져도 남의 사건이 샙니다.

- **도구 스키마에 `emp_id` 가 없습니다.** 모델이 고른 값이 권한이 되면 안 되므로 로그인 토큰에서만 옵니다.
- **사건 ID 를 이미 아는 조회도 예외 없이** 가시성 절을 겁니다. 모델은 앞 답변에서 본 ID 를 다음 질문에 그대로 씁니다.
- 권한 밖 접근은 **"없는 사건"과 같은 문구**로 막습니다. "권한이 없습니다"는 그 사건이 존재한다는 사실을 알려 주는 셈입니다.
- **"조회 가능"과 "내가 담당"을 다른 절**로 둡니다. 건수를 셀 때는 담당 절을 씁니다. 콘솔 화면과 숫자가 갈리면 사용자가 무엇을 믿을지 모릅니다.

### 2. 작은 자체 호스팅 모델로 신뢰성을 만든다

사건 자료가 사외로 나갈 수 없어 사내 서버의 양자화 모델을 썼습니다. 도구 호출이 상용 대형 모델만큼 안정적이지 않다는 전제로 방어를 겹겹이 쌓았습니다.

| 문제 | 대응 | 위치 |
|---|---|---|
| 도구 없이 금액을 답했는데, 실제 값은 비어 있었고 이전 답변의 다른 금액을 보고 지어낸 것이었다 | 답에 사실값(금액·건수·날짜)이 있는데 도구 호출이 0회면 `tool_choice: "required"` 로 한 번 더 | [`guard.py`](backend/app/agent/guard.py) · [`loop.py`](backend/app/agent/loop.py) |
| 작은 모델은 숫자를 비우거나 문자열로 준다 | 스키마를 주고도 실행부에서 정수 캐스팅·범위 클램프·enum 화이트리스트. 필수값이 없으면 "되물어라"를 돌려줌 | [`registry.py`](backend/app/agent/registry.py) |
| 모델이 링크·사건번호를 지어내면 엉뚱한 사건으로 간다 | 모델이 쓴 링크는 지우고, 바로가기는 도구가 돌려준 ID 로 서버가 만든다 | [`postprocess.py`](backend/app/agent/postprocess.py) |
| 내부 제어 토큰이 본문에 흘러 화면에 노출됐다 | 토큰을 지우지 않고 **그 앞에서 잘라낸다**. 지우기만 하면 뒤에 딸려 온 중복 문단이 남는다. 스트리밍 중에도 조각 경계에 걸친 토큰을 붙잡아 둔다 | [`guard.py`](backend/app/agent/guard.py) · [`loop.py`](backend/app/agent/loop.py) |
| 컨텍스트가 16K 로 좁다 | 토크나이저 없이 한글/ASCII 비율로 보수적 추정 → 긴 텍스트부터 자르고, 목록은 뒤에서 자르되 **몇 건 줄였는지 표시**. 통째로 버리면 모델이 "없다"로 읽는다 | [`context.py`](backend/app/agent/context.py) |
| 도구 실패를 예외로 올리면 모델이 같은 도구를 그대로 다시 부른다 | 실패를 오류 문자열 결과로 돌려준다. 모르는 도구 이름도 마찬가지 | [`registry.py`](backend/app/agent/registry.py) |
| 도구만 부르다 답 없이 끝난다 | 마지막 회차에는 도구를 주지 않는다 | [`loop.py`](backend/app/agent/loop.py) |
| 프롬프트 처리에 1,465토큰 기준 약 12초 | 기동 시 캐시 예열(두 번째부터 약 0.5초). 날짜·사용자 이름은 system 이 아니라 user 메시지에 둬서 **system 접두사가 모든 요청에서 같은 바이트**가 되게 함 | [`prompt.py`](backend/app/agent/prompt.py) · [`llm.py`](backend/app/agent/llm.py) |

### 3. 쓰기는 제안까지만

모델은 DB 를 직접 고치지 못합니다. 쓰기 도구는 전부 **제안**만 만들고, 실제 반영은 사용자가 카드에서
**반영**을 누른 뒤 별도 엔드포인트로만 들어옵니다. 읽기는 틀려도 다시 물으면 되지만, 쓰기는 틀리면 되돌려야 하기 때문입니다.
읽기/쓰기 도구를 파일 단위로 나눈 것도 같은 이유입니다 ([`tools_read.py`](backend/app/agent/tools_read.py) / [`tools_write.py`](backend/app/agent/tools_write.py) / [`writes.py`](backend/app/writes.py)).

- **부분 수정이 다른 칸을 날리던 문제** — 기존 CRUD 가 안 넘긴 칸을 `None` 으로 덮어써서, 면담 내용만 고치려다 변호사 코멘트가 지워졌습니다. 바꾸는 칸만 `SET` 합니다.
- **이어쓰기는 서버가 합친다** — "한 줄 더 추가해줘"에서 모델에게 전문을 다시 쓰게 하지 않고 추가분만 받습니다. 옮겨 적다 문단을 한 번 더 복사하는 일이 실제로 있었습니다.

### 4. 되묻기는 말이 아니라 UI 로, 알림은 먼저

- 후보가 여럿이면 모델에게 목록을 적게 하지 않고 **도구 원본을 선택 버튼**으로 올립니다. 사건 선택과 처분권자 선택이 동시에 뜨면 무엇을 고르라는 건지 알 수 없어서, 한쪽이 뜨면 다른 쪽은 억제합니다.
- **브리핑**은 모델을 부르지 않는 결정적 규칙입니다 ([`briefing.py`](backend/app/briefing.py)). 종류별로 3건만 보여 주고 나머지는 건수로 알립니다. 매일 스무 줄이 뜨면 아무도 읽지 않습니다.

### 5. 운영에서 겪은 것들

- **점검용 호출이 남의 대화방을 오염** — 수동 점검으로 부른 대화가 그 사용자 기록에 쌓였습니다. `persist=false` 로 분리했습니다.
- **SSE 가 끝날 때까지 안 보임** — 리버스 프록시 기본 버퍼링 때문이었습니다. `X-Accel-Buffering: no` 헤더를 붙였습니다.
- **스트리밍 동안 DB 커넥션이 묶임** — 인증 의존성을 서명만 검증하는 경량 의존성으로 바꾸고, 커넥션은 필요할 때만 짧게 엽니다.
- **"새 대화"는 삭제가 아니라 새 세션** — 지우면 기록 목록이 비어 버립니다. 세션 제목은 첫 질문을 그대로 씁니다. 요약 제목을 만들려면 모델을 한 번 더 불러야 하는데, 첫 질문보다 낫다는 보장이 없었습니다.

LLM 을 대본대로 답하는 가짜 클라이언트로 바꿔, 루프와 안전장치를 결정적으로 검증합니다.


| 파일 | 검증하는 것 |
|---|---|
| `test_visibility.py` | 스키마에 emp_id 없음 · 아는 ID 로도 남의 사건 조회 불가 · 없는 사건과 같은 문구 · 열람 권한은 조회만, 건수 제외 |
| `test_loop.py` | 사실값 무근거 시 재조회 강제 · 병렬 도구 실행 · 마지막 회차 도구 제거 · 선택 버튼 · 제어 토큰 차단 · 이력 8턴 제한 |
| `test_writes.py` | 확인 전 DB 불변 · 부분 수정 시 다른 칸 보존 · 이어쓰기 서버 병합 · 본인만 1회 반영 |

| `test_api.py` | 위조 토큰 거부 · 브리핑 · 대화 기록 사용자 격리 · 점검 호출 미보관 · 제안→반영 흐름 |

## 실행

```bash
pip install -r backend/requirements.txt
cd backend
python scripts/generate_data.py            # 합성 데이터 생성 (사건 320건)

# OpenAI 호환 서버 주소 (vLLM, Ollama 등)
export LLM_BASE_URL=http://localhost:8001/v1
export LLM_MODEL=<모델 이름>
uvicorn app.main:app --reload --port 8000
```

→ http://localhost:8000 · 상단에서 데모 사용자를 고를 수 있습니다.
